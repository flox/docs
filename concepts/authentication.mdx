Starting in **early October 2026**, several Flox CLI commands will require
authentication with a free Flox account.

## What's changing

Several Flox commands have always run through Flox cloud services for search,
indexing, package resolution, and environment operations. Beginning in early
October, every command that resolves packages against the Flox catalog will
require authentication. A command resolves packages when:

- [`flox install`](/man/flox-install) adds a package from the catalog.
- You run [`flox upgrade`](/man/flox-upgrade), including
  `flox upgrade --dry-run`.
- You run [`flox run`](/man/flox-run).
- A command has to lock the environment because `manifest.lock` is missing,
  or because you added or changed a catalog package or a system. This covers
  [`flox activate`](/man/flox-activate), [`flox edit`](/man/flox-edit),
  [`flox list`](/man/flox-list), [`flox uninstall`](/man/flox-uninstall),
  `flox services`, [`flox build`](/man/flox-build),
  [`flox develop`](/man/flox-develop),
  [`flox containerize`](/man/flox-containerize) and
  [`flox include upgrade`](/man/flox-include-upgrade).

Changing `[vars]`, `[hook]`, `[profile]` or `[services]` locks the environment
without contacting the catalog, so it needs no sign-in. Installing a flake
reference or a Nix store path doesn't use the catalog either.

| Command or situation | Sign-in today | After the change |
| --- | --- | --- |
| `flox push`, `flox publish` | Yes | Yes |
| `flox init -r`, and `flox install`, `flox uninstall`, `flox upgrade` or `flox edit` with `-r` | Yes | Yes |
| Any command with `-D` or `--default` | Yes | Yes |
| `flox pull` or `flox activate -r` of a private environment | Yes | Yes |
| Custom catalog packages that aren't on your machine yet | Yes | Yes |
| `flox install` of a catalog package | No | Yes |
| `flox upgrade`, including `--dry-run` | No | Yes |
| `flox run` | No | Yes |
| Any command when `manifest.lock` is missing, or a catalog package or system changed | No | Yes |
| `flox init` in a project where Flox detects Node.js, Python or Go | No | Flox creates the environment; its package suggestions need sign-in |
| `flox pull` of a public environment | No | No, unless it adds your system to the environment |
| `flox activate` with a current lockfile | No | No |
| Editing `[vars]`, `[hook]`, `[profile]` or `[services]` | No | No |
| `flox install` of a flake reference or Nix store path | No | No |
| `flox build` with a current lockfile | No | No |
| `flox search`, `flox show` | No | No |

<Accordion title="Do I need to do anything?">
  Probably not, and if you do it's one command. Find the row closest to how you
  use Flox.

  | What you're doing | Sign in? | What to do |
  | --- | --- | --- |
  | Activating an environment whose lockfile is current | No | Nothing |
  | Looking up packages with `flox search` or `flox show` | No | Nothing |
  | Adding, upgrading, or changing packages in your own environment | Yes | Run `flox auth login` once |
  | CI that activates an environment with a committed, current lockfile | No | Nothing |
  | CI that installs or upgrades packages each time | Yes | Give it a [token](#ci-and-automation) |
</Accordion>

## What stays the same

[`flox activate`](/man/flox-activate) does not require authentication for an
environment that already has a current lockfile. If your daily workflow or CI pipeline
simply activates an existing environment that relies on public packages, nothing
changes for you.

[`flox search`](/man/flox-search) and [`flox show`](/man/flox-show) stay open
too, so browsing the catalog needs no account. So does pulling a public
environment with [`flox pull`](/man/flox-pull).

Private packages and environments continue to require authentication as they
do today, and so does [publishing](/concepts/publishing). Nothing about those
changes.

## Who on your team needs an account

After the change, people who change packages need an account: anyone who adds
or upgrades catalog packages, changes a catalog package's version, package
path or package group, adds a system, locks an environment that has no
`manifest.lock`, or runs `flox run`. People who push environments or publish
packages need an account today.
People who only activate an environment with a committed, current
`manifest.lock` don't need an account, unless the environment uses custom
catalog packages that aren't on the machine yet, or is a private FloxHub
environment.

When they activate a FloxHub environment, it fetches its latest state from
FloxHub on first use and during the background upgrade check, whether or not
they're signed in. A private FloxHub environment needs sign-in.

The background upgrade check that each `flox activate` starts sends the
environment's package list to the catalog only when you're signed in. It sends
the list at most once a day for each lockfile, and on every activation while
that request fails.

Without an account, Flox still receives telemetry with a device ID unless you
turn telemetry off, and FloxHub logs each request with your IP address. See
[What Flox collects](/concepts/data-collection).

## Why we're doing this

Flox has grown from an open source CLI into foundational infrastructure used
across developer machines, CI, build systems, and increasingly AI agents. As
usage has grown exponentially, so has our responsibility to operate the cloud
services behind Flox reliably and to keep improving them based on how they're
actually being used.

Requiring authentication for the commands that interact with those services
gives us a better foundation for understanding those workflows, operating the
service reliably, and investing in the parts of Flox people depend on most. It
also gives us better standards around abuse prevention.

When you're signed in,
[CLI telemetry](/concepts/data-collection#cli-telemetry) events carry your
FloxHub account ID.
[What Flox collects](/concepts/data-collection) lists everything Flox records.

We're intentionally keeping `flox activate` available without an account for
public environments. If you're consuming an environment someone else
maintains, you do not need to create an account just to use it.

To be clear: this is not a paywall. The free tier keeps the same capabilities
it has today. You'll need a free account for the commands above, not a paid
subscription.

## Signing in

FloxHub has made it easy to login. How you sign in depends on where you're
running Flox.

<Tabs>
  <Tab title="On your machine">
    Run [`flox auth login`](/man/flox-auth) and follow the browser prompt. You
    can log in with an existing GitHub, Google, or GitLab account. If you don't
    have an account, the same flow creates one.

    ```bash
    flox auth login
    ```

    You do this once per machine. Paid customers can also authenticate with
    their own SSO provider — see [Enterprise SSO](/concepts/enterprise-sso).
  </Tab>
  <Tab title="No browser">
    Over SSH, inside a container, or anywhere a browser can't open, use a
    token instead. A
    [personal access token](/concepts/personal-access-tokens) signs the CLI in
    as you. A [service account](/concepts/service-accounts) token signs it in
    as your organization. The CLI reads either one from the same variable.

    ```bash
    export FLOX_FLOXHUB_TOKEN=<your-token>
    ```
  </Tab>
</Tabs>

You can also sign in on the web at [hub.flox.dev](https://hub.flox.dev).

## CI and automation

Automation breaks quietly, so it's worth handling before anything else. Two
ways through:

- **Commit your lockfile.** A pipeline that activates an existing environment
  against a committed, current `manifest.lock` needs no token. Without a token,
  it resolves no packages. You get reproducible builds and one less network
  dependency out of it, which is worth doing anyway.
- **Or give the pipeline a token.** Pipelines that run `flox install`,
  `flox upgrade`, or any of the other commands above do reach the catalog. So
  does `flox build` when the lockfile it's building against is out of date.
  Issue a token in FloxHub and set it as `FLOX_FLOXHUB_TOKEN` from your CI
  platform's secret store. The pipeline or agent then runs Flox commands
  without user interaction.

A [personal access token](/concepts/personal-access-tokens) works on any
account, including a free personal one, and acts as you. A
[service account](/concepts/service-accounts) token belongs to an organization
instead, so the pipeline keeps running after someone changes teams or leaves.
The CLI reads both from the same variable.

The [CI/CD tutorial](/tutorials/ci-cd) covers setup on specific platforms.

<Warning>
  Service account and personal access tokens need **Flox CLI 1.14.0 or newer**.
  Older releases reject the token as invalid and clear it, so the pipeline
  fails as though it were never set. Check with `flox --version`, and see
  [installing Flox](/install-flox/install) to upgrade.
</Warning>

## FAQ

<AccordionGroup>
  <Accordion title="Do I have to pay for Flox now?">
    No. Flox has always had a free tier and we keep adding to it. You need a
    free account, not a paid subscription.
  </Accordion>

  <Accordion title="What happens to my CI pipelines?">
    If your pipeline uses one of the commands listed above, add a personal
    access token or a service account token to your CI secrets before October.
    Pipelines that only activate an existing environment against a committed,
    current lockfile carry on unchanged.
  </Accordion>

  <Accordion title="What's the exact cutoff date?">
    Early October 2026. We'll follow up with the specific date and send a
    reminder before the change takes effect.
  </Accordion>

  <Accordion title="What if I miss the deadline?">
    `flox push`, `flox publish`, and `flox init`, `flox install`,
    `flox uninstall`, `flox upgrade` or `flox edit` with `-r`, and any command
    with `-D`, prompt you to sign in when you run them in a terminal. Commands
    that resolve packages don't prompt you. They fail with an error from the
    catalog. Run `flox auth login`, then run the command again. Signing up
    takes under a minute.
  </Accordion>

  <Accordion title="Do you have an option that isn't public FloxHub?">
    Yes. FloxHub Enterprise runs on your own infrastructure. Email
    hello@flox.dev for more information.
  </Accordion>

  <Accordion title="Does Flox collect my code?">
    Flox doesn't upload your source files, unless a `flox publish` build
    copies them into the package. When you push an environment, FloxHub stores
    its `manifest.toml` and `manifest.lock`, including `[vars]` values and hook
    scripts. Each push also stores a history entry with your login name,
    hostname and `flox` command line. FloxHub makes environments you push
    public by default. Telemetry contains your search terms and
    the names of your packages and environments. See
    [What Flox collects](/concepts/data-collection).
  </Accordion>

  <Accordion title="What does signing in tell Flox?">
    When you're signed in,
    [CLI telemetry](/concepts/data-collection#cli-telemetry) events carry your
    FloxHub account ID. Flox then links your device ID to your account,
    including events the device sent before you signed in. FloxHub records your
    handle and account ID with each catalog request. Flox joins the account ID
    to your account's email address in its analytics data. See
    [What Flox collects](/concepts/data-collection#cli-telemetry).
  </Accordion>

  <Accordion title="Can our developers use Flox without accounts?">
    Yes, if they don't change packages. Developers who activate environments
    with a committed, current lockfile, search the catalog, or pull public
    environments don't need an account. After the change, anyone who adds or
    upgrades catalog packages needs one. Without an account, Flox
    still receives telemetry with a device ID unless you turn telemetry off.
    FloxHub logs each request with the developer's IP address. See
    [Who on your team needs an account](#who-on-your-team-needs-an-account).
  </Accordion>

  <Accordion title="Can we turn off telemetry for everyone?">
    Set `disable_metrics = true` in `/etc/flox.toml` on every machine, and
    export `FLOX_DISABLE_METRICS=true` or `DO_NOT_TRACK=1` from a system-wide
    shell profile. `DO_NOT_TRACK` also overrides a user's
    `FLOX_DISABLE_METRICS=false` and `disable_metrics = false`. A user can
    override or unset each of these, so Flox can't enforce the setting. To
    enforce it, block Flox's telemetry and error-report endpoints at your
    network edge. Telemetry shares `api.flox.dev` with the API, so blocking it
    needs a proxy that filters by path. See
    [Turn off telemetry](/concepts/data-collection#turn-off-telemetry).
  </Accordion>

    [Flox Discourse](https://discourse.flox.dev/), or email support@flox.dev.
